# Alt Mean Reversion Bot

这是 2026-10-23 的 Windows 源码安装包。项目面向 Binance USDⓈ-M USDT 永续合约，提供本地 Paper 模拟、USDⓈ-M Demo 试运行、策略回测和诊断工具。

安装包不是独立 EXE，也不是离线依赖包。需要 Windows x64、Python 3.11 或 3.12，以及安装时访问 Python 包索引的网络。首次策略运行还需要访问 Binance 公共行情 API。

默认运行方式是本地 Paper：只读取公开行情，在本地模拟成交，不创建私有交易所客户端，也不发送订单。安装脚本只准备项目虚拟环境和依赖，不启动服务、不连接账户、不注册 watchdog 或计划任务。

独立的旧版 LOW/HIGH 均值回归 Paper Runner 可用以下命令启动：

```powershell
.\.venv\Scripts\python.exe .\scripts\run_legacy_mr_paper.py
```

它使用热度 Top 20、4H LOW/HIGH 与已收盘 1H 方向信号、BTC 大盘风险拦截、当前共享风控参数及 EMA20 中轨回撤退出。账本单独保存在 `data/paper/legacy_low_high_portfolio.json`，默认虚拟资金为 5,000 USDT；日志保存在 `logs/legacy_low_high_paper.log`。它仅连接公开行情，不读取 Demo 账户或发送交易委托。加 `--once` 可运行一个行情周期后退出。

需要单独查看这份旧版 Paper 账本时，在另一个 PowerShell 窗口运行。旧账本预览使用 8768 端口，8767 留给新的独立策略：

```powershell
.\.venv\Scripts\python.exe .\scripts\run_dashboard.py --state .\data\paper\legacy_low_high_portfolio.json --port 8768
```

## 有意排除

真实环境文件、API 密钥、账本、订单／仓位状态、市场缓存、研究缓存、运行日志、虚拟环境、Python 缓存和当前电脑上的计划任务或快捷方式均未打包。该 ZIP 是干净源码快照，不能恢复另一台电脑的余额、模拟状态、Demo 订单或历史表现。

现行策略已提供独立 Binance Futures Lead Portfolio 实盘入口。该入口必须使用 Lead Portfolio 专用 API Key 和独立账本；手动启动 Runner 或启用看护器时都要在终端输入 `LEAD` 确认。账户连接及只读初始化已核验，真实委托和跟单成交同步尚未验收。前台启动方式会随启动它的 PowerShell 终止；如需关闭 PowerShell 后继续运行，先按 `Ctrl+C` 停止前台实例，再使用 `run-lead-live-background.ps1`。不得使用普通 Futures API Key 或把密钥写入项目文件。

默认情况下，Lead Runner 仍会因账本外仓位而拒绝同步。若要让它接管手动开仓，必须显式添加 `--adopt-manual-positions`（后台脚本与看护器使用同名 `-AdoptManualPositions` 开关）。接管以不超过 7 天的连续明确窗口回放最近 90 天且少于 1,000 条的该币成交，核对边界、重复记录和当前仓位，并使用入场时已收盘 1H／4H 行情重建 ATR、摆动结构和状态；无法完整重建时保持不一致并暂停开仓／仓位管理。它按现有自适应止损计算，保留更紧且已验证的 `STOP_MARKET reduceOnly` 止损，否则先确认新策略止损有效再替换较宽止损。若止损已被市场穿越、订单不唯一或复核失败，不会自动市价平仓或猜测入场信息。接管后使用已有退出管理；机器人自主入场、止损与退出策略不变。Lead 使用单向持仓，同一币种的手动与机器人成交已合并时按交易所汇总仓位管理，无法拆成两笔独立仓位。真实手动持仓的接管及退出尚未完成运行验收。

入场响应不明时，Runner 会按保存的 `clientOrderId` 对账，期间暂停新开仓和账本外手动仓位接管。 市价委托提交或首次成交回查遇到短暂查无订单或超时时，最多按同一客户订单编号回查 4 次。仅在订单标识、方向、数量和成交均价核验通过后继续安装原策略止损。超过回查预算则留待对账。若交易所返回 `OrderNotFound`，只有提交已过 5 分钟、仍在未成交订单的 3 天历史保留窗口内，并且从提交前 1 分钟至核查时该币的订单历史、成交历史、当前普通挂单和条件挂单均经成功查询确认为空、两次持仓检查均为空，才将该尝试记为 `not_filled`，保存核查证据并结束阻塞。任何查询失败、数据异常、同币种活动或已记录成交结果都会保留待确认状态；不会补发原订单或重放已过期信号。

`run-lead-watchdog.ps1` 可在一次 `LEAD` 确认后隐藏看护实盘 Runner：已有正确实例时直接接管，进程退出后按退避规则恢复。活进程的账户或心跳异常只写本地日志，不强杀。`-Status` 查看进程与账本健康，`-Stop` 只停止看护并保留 Runner；主动停止 Runner 前先停止看护。看护授权仅持续到该看护器退出或 Windows 重启，届时需重新启用。详见 [实盘看护说明](INSTALL_WINDOWS.md#lead-runner-看护器)。

Lead 持仓在 Binance 界面手动平仓后，Runner 会用只读逐笔成交记录核验该仓位从开仓到发现空仓期间的反向成交。成交数量吻合且费用数据完整时，回填平仓时间、价格与净盈亏；记录不足或无法唯一核实时保留待核验状态，不猜测盈亏。

启用 `--adopt-manual-positions` 后，源码现已支持已接管仓位的持续成交对账：手动同向加仓／减仓更新总数量、均价、剩余入场费及已实现盈亏，按实际总量先核验新保护再撤旧保护，不放宽活动止损，保留持仓计时、结构及已完成退出阶段；清仓结束当前信号；反手或清仓后重新开仓先结算旧仓，再使用新入场时已收盘行情重建新仓上下文。成交游标保存在既有持仓管理字段中，重启重试不会重复记账；同一毫秒分笔成交、连续加减及数量／均价不变的往返也按成交识别。手动变更后的交易排除在自主策略绩效样本外。处理随账户同步发生，仍存在轮询和接口延迟，新增或反手仓位在止损核验完成前不能视为已受保护。新版本已部署到 Lead；真实连续变更的自然成交验收仍待完成。

变更无法核实时，Dashboard／账本保留具体阶段和原因，暂停账户新增风险；相关币暂停主动策略管理，其他仓位只有在新鲜账户快照与各自保护单核验通过后才继续管理。待确认的机器人委托优先按原编号对账，不将其成交重复记为手动变更；策略平仓前发现数量／均价改变会先要求对账，不按旧账本直接发单。

Demo／Lead 主动策略平仓先保留保护单，发送 `reduceOnly` 市价委托并核实仓位归零后，才清理已识别的残留止损。Runner 在发单前将平仓请求编号写入现有订单账本；响应不明时仅回查同一编号，暂停新开仓及策略管理，不重复提交。部分成交、请求仍不明或止损清理失败时保留待对账状态；尚有仓位时保留原保护单。止损与主动平仓并发成交时，按核验后的实际成交回填，避免把局部成交当作整仓盈亏。此修复需部署新 Runner 后生效。

要在 Lead Runner 中接管账本外的手动持仓，可在看护器首次启用时使用 `.\run-lead-watchdog.ps1 -AdoptManualPositions`。看护器会在后续恢复时保持同一开关；已有看护器或 Runner 不会自动切换模式，切换前须按实盘操作流程停止并重新启用。

## Lead 实盘资金与风险参数

仅 Lead 后续机器人新开仓启用：单币名义仓位不超过当前权益 60%，先按止损与费用预算计算数量，再在 3–10 倍中选择满足安全缓冲的最高杠杆；不再用目标保证金乘杠杆扩大数量。单笔计划风险不超过权益 2%，组合风险不超过权益 4%，由本金止损风险和浮盈回吐风险构成；浮盈回吐金额按 15% 权重计入。原有总名义仓位 180%、同向 90%、最多 5 币限制继续执行。Demo 资金参数、各模式的信号、结构／ATR 止损和触发价格类型保持原样；2R 追踪仓位的时间豁免按下文规则执行。

组合预算逐仓计算。本金风险是入场价到当前已核验活动止损之间的止损损失（最低为零）及往返费用；浮盈回吐风险是从当前标记价回落到入场价或活动止损中较有利一侧的金额，再乘 15% 计入 4% 上限。未盈利部分不计为回吐，已有仓位不相互抵扣；新单计入完整的入场到止损风险及往返费用。不使用初始止损替代活动止损。手动接管持仓同样占用组合预算，但不自动调整其原杠杆或数量。预算不足会减少或跳过新单，已有仓位不为释放预算而收窄止损。账户、标记价格、活动止损或待确认入场状态无法核实时暂停新风险。

新单读取签名接口返回的实际维持保证金及名义金额档位，按逐仓公式估算强平价，并在强平名义金额跨档时重算。入场到强平的距离至少是入场到策略止损距离的 2 倍，止损到强平价的距离至少为强平价的 1%；不满足则降杠杆，3 倍仍不满足就跳过。保证金和全额预估费用必须充足，禁止自动追加保证金。成交后读取实际强平价、杠杆、逐仓模式及 `CONTRACT_PRICE` 活动保护单，复核失败则在保留原止损的同时尝试 reduceOnly 退出新仓，随后保持对账阻塞，核清成交和盈亏后才能继续。未确认响应的恢复也执行该校验，不补发旧单。跳空、滑点和网络故障仍可能使实际损失超过计划值。

Lead 日内停开阈值为 10%，Demo 仍为 4%。沿用上海交易日的日初权益基准，计入已实现与未实现盈亏；触发后继续管理已有仓位，至下一交易日才解除停开。加载新参数不重置当日基准、亏损记录或已触发的停开锁。参数源为 `configs/default.yaml` 的 `lead_risk`，运行账本通过 `lead_risk_policy_loaded` 和新单的 `lead_entry_capital_verified` 事件记录加载与验证结果。实际新杠杆订单成交尚需自然信号验收，不为测试额外开仓。

新源码在每次有效账户同步时检查日内停开，无开仓信号时也检查；陈旧、无效或失败的快照不能重置基准。状态变化写入 `daily_risk_day_started`／`daily_risk_halt_triggered`。初步数量计算、风险审批及信号止损拒绝写入 `entry_risk_rejected`，最终预检保留 `entry_preflight_decision`；记录原因、阶段、信号时间、权益、风险／名义预算及计划数量，最终预检关联同一 `clientOrderId`。这些记录沿用现有 JSON 账本，需部署新 Runner 后产生。

Lead 的新单预检包含只观察的 `entry_liquidity`。使用同一份已通过时效校验的五档盘口，记录买卖价差、入场和反向减仓的可见深度、按计划数量逐档计算的均价及滑点。滑点以同侧最优价为基准，价差另记。五档不足以覆盖计划数量时，均价及滑点记为空。

建议数量以风险预检的原数量为上限，取买卖两侧各自最优价向外 `risk.max_slippage_pct` 范围内较薄一侧的 50% 深度，再按数量步长向下取整。建议不足最低委托量或名义额时记为跳过。50% 是本阶段的观察假设，现行滑点参考为 0.15%；记录中 `_pct` 字段均为小数比例，例如 `0.0015` 表示 0.15%。预检和实际成交事件会保留观察值，成交事件另记实际价格相对预检最优价的滑点。反向深度反映预检时的盘口，止损触发时深度可能变化。

## USDⓈ-M Demo 与 Lead 共用的开仓门槛

Lead 的候选池源码现已改为每根 1H 收盘后扫描全部合格合约。交易资格仍使用合约状态、上市时间、24 小时成交额和交易所 Lead 合约白名单；白名单来自已核验的 `sapiGetCopyTradingFuturesLeadSymbol`，不是旧 Top20。结构条件使用至少 55 根已收盘 UTC 日线的 EMA50 方向、最新已收盘 1H 价格相对已收盘 4H EMA50 的偏离，以及原有 `max(1%, 0.8 × 4H ATR14 / 4H close)` 门槛。结构扫描要求行情连续、新鲜且有效，不再经过旧评分的 Top20 截断。日线价格等于 EMA50 时结构不成立。

结构池以 `strategy_tag` 标记 `MR`／`VSB`，旧记录缺省为 `MR`。每小时单次遍历全部合格币，使用同一日线方向及动态偏离门槛，按 if／elif／else 互斥路由：逆向偏离 `adverse_dev >= d` 且当前连续挤压不足 6 根归 MR；`-1.2d <= adverse_dev < d` 且连续挤压 6–36 根归 VSB；其余剔除。做多逆向偏离为 `(4H EMA50 - 1H close) / 4H EMA50`，做空相反。MR 连续挤压满 6 根即移出，原 MR 的反转确认、ATR14、止损及退出参数保留。方向或策略改变建立新记录；同一路由持续成立保留首次入池时间。读取失败或全市场返回缺项时标为待核验并暂停该币新开仓，其他完整币继续评估。池状态仍写入 `mr_candidate_pool`，`watchlist` 展示有效及待核验成员。重启重新核验行情，池成员变化不替代持仓退出或已提交限价单管理。

VSB 使用已收盘 1H 的 BB（SMA20、总体标准差、2 倍带宽）与 KC（EMA20、1.5 × Wilder ATR14）。BB 上轨严格低于 KC 上轨且下轨严格高于 KC 下轨才算挤压。保存完整连续段的根数、最高／最低价、中轴及均量；指标预热截断的挤压段不作为 VSB 有效箱体。首次解除挤压的当根仍携带前序 6–36 根箱体供同小时触发检查，下一根不重放；突破根不计入箱体和均量。

### VSB 运行模式与影子账本

`configs/default.yaml` 的根字段 `vsb_execution_mode` 支持 `DISABLED`、`SHADOW`、`LIVE`，默认 `SHADOW`。环境变量 `VSB_EXECUTION_MODE` 优先于 YAML，非法值拒绝启动。配置在 Runner 启动时读取；修改源码或配置后需要按既有实盘流程重启才能生效。

- `DISABLED`：不接收新的 VSB 结构候选或订单，MR 按既有规则运行。
- `SHADOW`：保留单一结构池中的 VSB 标签，在实盘候选扫描及风险审批前剔出 VSB；MR 优先完成发单后，再用公共行情评估影子信号。独立写入 `data/vsb_shadow_ledger.json`，固定初始虚拟权益 10,000 USDT，资金、仓位、冷却、日内状态、限价单和风险审批均属于影子账户，不计入 Lead 的 4% 风险、名义敞口或 5 币名额。影子代码不接收实盘执行器，不提交 Binance 委托；磁盘或行情失败仅记录影子异常，不修改 Lead 同步状态。
- `LIVE`：新的 VSB 信号通过原实盘风险、成交核验和保护单管道，实际下单仍需要已有 Lead 启动授权及全部安全检查。该配置值本身不会启动或部署实盘。

### Lead ATR 偏离审计与白名单前瞻记录

Lead Runner 每根 1H 扫描继续记录热度榜原始排名及合约白名单过滤结果，事件名为 `lead_whitelist_ranking_shadow`。偏离门槛已由影子观察提升为实际入场条件，Paper／Demo／Lead 共用 `max(1%，0.8 × 已收盘 4H ATR14 / close)`，不会使用未收盘 4H K 线或为该规则增加行情请求。

`atr_deviation_entry_shadow` 保留固定 1% 与 ATR 门槛的对照记录：固定 1% 候选通过时间过滤、有效止损、日线方向、结构冷却和 EMA9 后，先记录对照，再执行 ATR 拦截。`active_deviation_rule`、`active_threshold_pct` 和 `active_decision` 标明当前实际规则及判定；旧记录不含这些字段，仍按当时的纯影子观察解释。ATR 不可用记为 `UNAVAILABLE` 并拒绝该候选，审计日志写入失败不绕过实际 ATR 条件。

关联键继续进入扫描和发单尝试，实际发单预检会记录冻结的 `deviation_threshold_pct`。资金费率、账户同步、报价、数量及风控审批仍须逐项通过。记录本身不是独立影子组合，也不能据此计算切换规则后的组合收益。此前三期研究结果属于当时版本的单因素对照，不含后来增加的 EMA9、资金费率翻转与动态限价。

8766 在账户模式、持仓和合约设置检查完成后，发单前再次获取对应交易所账户的五档盘口，做多使用最佳卖价、做空使用最佳买价。信号从 1H 收盘至最终发单检查不得超过 `execution.confirm_delay_sec_max`（当前 60 秒）；盘口时间戳必须有效且不晚于本地观察时间，盘口年龄不得超过 `execution.entry_quote_max_age_sec`（当前 15 秒）。缺失、异常或过期报价禁止该次开仓。复核使用原信号的已收盘 4H EMA、1H 开盘价、ATR 和结构位，检查偏离及方向条件、结构失效和原计划止损，并按最新报价重算止损距离、数量和风控。首个候选被拒后，仍可在有效期内按原排名评估下一候选。

`execution.entry_adverse_atr_observe` 当前为 `[0.05, 0.10, 0.15]`，只记录各档不利报价偏移是否超限，不据此拦截。`entry_preflight_decision` 记录实际评估、报价和最终检查时间；`entry_execution_quality` 记录发单前本地时间、成交时间、公共／账户执行报价、档位数量与 ATR 偏移分解；公共报价不可用时保留缺失原因，不作为账户报价的替代。两个报价并非同时采集，事件保留时间差，最佳一档数量也不保证整笔市价单能按该价格成交。`entry_cycle_timing` 记录行情准备和入场评估完成时间。60 秒约束的是发单前信号有效性，市价单最终成交价及完成时间仍取决于交易所。

8766 的退出处理进度与入场扫描进度独立记录。入场扫描在账本的 `mr_entry_scan` 保存本根 1H K 线、候选名单、方向、尝试次数与处理结果。已完成的候选不会因轮询、重启或同根 K 线内开平仓而重复入场；尚未完成的候选只能在原收盘时刻起算的 60 秒内继续。候选评估和发单前准备中的单币 `BadSymbol` 等确定性错误会记录后跳过；暂时性读取失败先让其他候选完成，再最多补一次。认证、限流、账户异常或程序错误暂停本轮新开仓，正常候选仍遵循原有排名、入场条件与风控。

交易所模式开仓会先在 `mr_entry_attempts` 持久化稳定的 `clientOrderId`，最终发送前再保存实际数量和止损位。保存失败时不发单；保存后也重新检查信号和盘口有效期。发单后响应丢失或保护止损结果不明时，暂停新开仓并按保存的订单标识查询订单、成交、持仓和保护止损，不自动补发市价单。重启后先进行同样的对账。仅当成交、持仓和保护止损一致时恢复本地持仓；查询不到订单、成交后已经平仓但平仓账目未核实、或保护止损无法确认时，继续暂停新开仓并记录原因，需后续核对处理。已确认的其他持仓继续使用现有退出管理，未知订单的保护单不做孤儿清理。

`entry_scan_outcome` 和 `entry_scan_finished` 记录单币结果及本轮状态；异常记录包含币种、阶段、公共／交易所接口类别、异常类型和是否可能已发单，不记录原始异常响应。扫描之外的接口错误记录 `entry_cycle_failed`，无法确认接口来源时标为 `unidentified`。已有持仓的报价状态变化和监控异常写入账本及运行日志，并带有 Demo／Lead 执行模式；当前没有配置外部推送通知。

## 8766 执行恢复与日志保护

Demo 或 Lead 启动时，暂时性网络读取失败最多尝试 3 次，间隔为 1 秒、2 秒；认证、限流和其他非暂时性错误直接停止启动。失败日志保留账户类型、阶段与异常类型，不输出签名请求内容。首次账户初始化失败时，不会写入一个尚未取得真实账户基准的新账本。

热度行情准备中的公开市场、全市场报价和单币 1H 数据读取，在原信号有效期内遇到暂时性网络错误可补一次读取。读取之间继续检查已有交易所持仓，错误携带请求阶段、接口类别及相关币种。原有 60 秒发单时效和 15 秒盘口时效继续生效，网络故障持续时仍可能错过候选。

账本原子替换的短暂重试耗尽后，Runner 保留内存中的交易状态，继续管理已确认的交易所持仓，并暂停新开仓，直到状态能够成功保存。连续保存失败复用本进程同一目标的临时文件，原账本在替换成功前保持有效；既有遗留临时文件不自动清理。发单前的持久化检查失败时不会发送订单；发单后响应不明仍进入原有对账流程，不自动重发。

entry_preflight_decision、开仓成交和 entry_attempt_outcome 使用相同的 clientOrderId。尝试结果记录未提交、提交中、成交完成或待对账，以及阶段和异常类型。发单前报价审计随尝试保存，重启恢复成交时可一并恢复质量记录。历史缺失事件不会被补写成未经证实的成交。

Runner 日志及未捕获异常堆栈会对 signature、API 凭据、token 和密码字段脱敏，并关闭堆栈局部变量输出。该保护只作用于加载新代码的进程；既有日志需要另行按指定范围处理。

Windows 看护器明确以 UTF-8 读取账本，避免默认 ANSI 编码损坏中文币种名称并误报 JSON 解析失败或仓位不一致。

8766 交易所账本的 `funding_paid` 历史字段保存带符号资金费收入，正数为收入、负数为支出；净盈亏为毛盈亏减手续费再加资金费收入。平仓满 5 分钟后，每 5 分钟复核最近 24 小时平仓的资金费；更早且尚未复核的平仓也补查一次。复核只匹配该币种实际持仓区间的资金流水，发现延后入账的资金费时更新原平仓净盈亏，并追加 `funding_reconciliation_adjusted`，保存调整前后值。流水查询失败、超过返回上限或持仓区间归属不唯一时保留原值等待核对。

## 8767 独立本地均值回归 Paper

8767 独立运行于本地 Paper，不读取 Demo 账户、不发送交易所委托，默认使用 5,000 USDT 虚拟资金。它每 5 分钟刷新最多 20 个通过准入过滤的均值回归候选；仅在新 1H K 线收盘后评估入场，使用最近收盘 UTC 日线方向门槛、已收盘 4H EMA50 和已收盘 1H 反转条件。还要求 1H EMA9 收复／跌破；资金费率仅在对候选方向不利且绝对值严格超过 `risk.funding_abs_block` 时拦截，费率缺失仍拒绝。普通振幅信号按原方式模拟成交；振幅超过 1.8×ATR14 时保存 3 小时回撤限价，后续新鲜公开报价触价才按限价模拟成交，到期放弃。通过 BTC 风险和仓位风控后执行。保护止损在浮盈达到 1 ATR 后锁定扣除费用和滑点后的 +0.2R，达到 1.5R 后提高至 +0.5R，达到 2R 后启动原有追踪算法；其他结构失效、布林中轨、行情状态、无进展及持仓时限退出保持原样。本地保护止损仍每轮使用实时价格监控。看护器每 15 秒运行一轮。

在项目根目录运行以下命令启动看护器。看护器会拉起 Paper Runner，并在 Runner 进程退出或账本心跳超时后重启：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\watch_mr_intrabar_paper.ps1
```

Dashboard 使用独立账本和 8767 端口：

```powershell
.\.venv\Scripts\python.exe .\scripts\run_dashboard.py --state .\data\paper\ema50_intrabar_portfolio.json --port 8767 --no-open
```

本地访问地址为 `http://127.0.0.1:8767/`。策略日志保存在 `logs/mr_intrabar_paper.log`，看护日志保存在 `logs/mr-intrabar-watchdog-YYYYMMDD.log`。

## 时间过滤的 fail-closed 与审计

8766／8767 的均值回归开仓均要求最新 1H K 线已收盘，时间戳按 K 线开盘时间加 1 小时计算。时间过滤只使用截至该收盘时刻的数据；至少要有 25 根连续完整 1H K 线，覆盖 ATR 和此前 24 根区间。收盘时间不匹配、历史不足、K 线断档、ATR 无效或 OHLCV 无效时，数据状态会标为不可用并禁止新开仓。8767 另会拒绝收盘超过 10 分钟的迟到信号；8766 在候选评估和最终发单前均用真实当前时间检查 `execution.confirm_delay_sec_max`，不再以循环开始时间和固定 10 分钟上限替代。

若均值回归条件本身形成候选，账本会写入 `entry_time_filter_decision`，记录候选方向、允许／拦截结果、原因、K 线 UTC／上海时间、脉冲 ATR 倍数、区间标记和 Runner／过滤器源码指纹。8767 对未收盘或迟到的 K 线记录 `entry_bar_rejected`。可在 Dashboard 对应账本状态中的事件记录和 Runner 日志中核对。

8766 的 LOW/HIGH 衰退退出现在会在每次持仓 1H 退出评估时写入 `regime_fade_evaluated`，包含持仓／当前 4H regime、1H 收盘进展 ATR 倍数、0.5 ATR 阈值及是否在热点榜。数据缺失或更高优先级退出先发生时写入 `regime_fade_check_skipped`；条件触发时先写 `regime_fade_exit_attempted`，交易所确认平仓后仍以 `paper_fill` 和 `long_regime_faded`／`short_regime_faded` 记录成交。以上事件仅用于审计，不改变退出条件。
